Corner · Technical Project · Phase 1

Instagram → the best ephemeral events in a city

PRD & Implementation Plan

The hard part isn't scraping Instagram — Apify does that. It's turning a noisy, meme-filled feed into a clean, deduplicated, trustworthy set of events pinned to real places — and keeping them fresh. Everything here optimizes for the three things that matter: clean data out of messy IG, identity & freshness, and a point of view on what “best” means.

The goal

01 What we're building

Events are Corner's missing, most time-sensitive layer.

Corner surfaces places friends love. The good events — pop-ups, dinners, shows, drops — live in Instagram captions, flyers, and reels, not on Eventbrite. The build is an ingestion pipeline that continuously converts NYC Instagram content into structured, deduped, map-ready events, ranked so the best rise to the top.

Non-goals for Phase 1 (design for them, don't build them): ticketing/RSVP, user-submitted events, cities beyond NYC, real-time push.

Product point of view

02 What “best” means

The brief says surface the best events — that's a ranking stance, not just ingestion.

SignalWhy it means “best”
Source authorityA trusted local curator beats a random repost
Scarcity / ephemeralityA one-night pop-up beats a standing weekly. Corner's whole angle is ephemeral.
EngagementLikes / saves / comments as a demand proxy
Proximity & timingNear the user, happening soon
Extraction confidenceWe only rank high what we're sure we understood

Ranking is a first-class output, not an afterthought — it's the product-judgment layer.

Surfacing it — event tiers, the way Corner tiers places

Corner already speaks in vibe tiers for places; events get the same language, computed from engagement (likes · comments · shares) aggregated across every post about that event — which the dedup model makes possible, since many posts resolve to one event_id. The three tiers are three different axes, not one popularity scale:

Lowkey
Hidden gem · quality

Low reach but a positive signal — trusted curator, or high engagement-rate for a small account. Guard: must mean “under-the-radar gem,” not “nobody cared.”

Popular
Magnitude

High total engagement across all observed posts. The steady, broadly-loved events.

Trending
Velocity

Engagement accelerating now — and/or several accounts posting it in a short window. Pairs directly with ephemerality: “blowing up right now.”

Two rules so the tiers don't lie: normalize on engagement rate (interactions ÷ the account's own baseline) so big accounts don't win everything, and apply time-decay so tiers recompute over an event's life — an event can move lowkey → trending → popular. The same freshness job that expires events recomputes tiers.

The core hard problem

03 Identity & dedup

Answering the one question a founder wrote down.

Founder question · Jake

“How do we make sure our ‘primary keys’ are accurate and unique?”

Short answer

You don't key on natural fields. (place, desc, time) is too noisy to ever be unique — descriptions are free text, times are written as “this Fri,” and the same event gets reposted five different ways.

1 · Surrogate key. Every event gets a UUID event_id. That's the real primary key — stable and unique by construction.

2 · Derived dedup signature — how we decide two extractions are the same event:

dedup_sig = venue_place_id + normalized_start_datetime (bucketed) + title/embedding similarity ≥ τ
  • venue_place_id comes from Google Places — canonical, not free-text — and hands us geo coords for the map for free.
  • normalized_start_datetime requires resolving relative dates first (§5). This is the linchpin — you can't dedup on a date you haven't normalized.
  • title match is fuzzy + embedding cosine, so “Devin Shaffer b2b” and “Devin Shaffer live” collapse.

3 · Re-posts attach, they don't duplicate. A second post about the same event becomes a new source row linked to the existing event_id — never a new event. That's also how we raise confidence (two sources agree) and enrich (one has the price, another the lineup).

The failure modes naive dedup breaks on

Failure modeNaive resultOur handling
Same event, two venues (a tour/crawl)Merged into one wrong eventSignature is per (venue×time); modeled as linked instances
Two events, one venue, same nightWrongly mergedTitle/embedding similarity threshold keeps them apart
Recurring series vs one-offExplodes into dupes, or collapses distinct nightsrecurrence_rule; each dated occurrence is its own row

The two stages you don't have yet — and why they matter most

  • B · Event-gate (the biggest gap). @newyorklocals posts memes and café recs, not just events. Extracting every post wastes vision cost and hurts precision — a meme shown as an event is worse than a missed one when the brief says surface the best.
  • D · Date resolution. Captions say “tonight,” “this Friday.” Resolve against the post's timestamp + timezone. Small, but load-bearing: without it you can neither rank by “happening soon” nor dedup by date.
Data quality

05 Messy IG → clean events

Extraction is where vision LLMs quietly fabricate. Design against it.

Fields (yours, kept): cover image, venue name, address, description, start/end datetime, RSVP deadline, capacity, age limit, cost, category, external link — plus source_url, source_account, per-field confidence, evidence_span.

Reels: don't run vision on every frame — sample keyframes + transcribe audio (Whisper) + read the caption. Most info lives in the caption and one flyer frame; escalate to dense vision only when those are thin.

Anti-hallucination rules

  • Per-field confidence — the model rates its own certainty.
  • Evidence span required — the caption text or image region a value came from.
  • null beats a guess — a missing price is fine; a confident wrong $27 / 21+ is a support ticket.

Venue accuracy (your Google Places step, sharpened): feed name + address to Places, take the top match above threshold, store place_id + lat/lng. No confident match → hold, don't drop (it may be a brand-new venue). This is what makes an event map-able.

Freshness

06 Ephemerality & lifecycle

Events aren't static rows — they have a life.

Model a status — upcoming → live → past → archived (+ cancelled). A scheduled job flips it by time and auto-hides past events from the map; the screenshots show a live “events nearby” rail, and stale events erode trust fast. Stories (24h TTL) are the most ephemeral and often richest event source — scrape them on a faster cadence than posts.

Scope

08 MVP & the golden test

Ship a hosted slice that proves the whole pipe.

  • Scrape ~5 seed NYC accounts.
  • Event-gate → extract → resolve date → resolve venue → structured JSON.
  • Dedup + store (Postgres + pgvector for embedding similarity).
  • A hosted webapp that is a faithful clone of the Corner app (see below), with source attribution.

UI parity — it should feel like Corner

A presentation requirement, not polish: the demo must read as “ships in the app tomorrow,” not “a pipeline with a rough UI.” Match the reference screenshots — map-first full-screen with circular pins, the category chips (top picks · eat · cafes · bars · events · go out, events selected by default), the “events nearby” list (venue headers + horizontal cards: cover, title, date, price), the bottom nav, and the top search bar. The lowkey / popular / trending tiers render as filter chips — Corner's own vibe-filter pattern — so the feature reads as native. Events show up both as map pins and in the list, off the same events table.

UI tech: React + MapLibre GL (free, no token) or Mapbox GL with a custom light style; event pins as custom HTML markers; the rest plain CSS. Reuse Corner's exact vocabulary, chip layout, pin style, and typography.

Golden acceptance test

The two reference IG posts the interviewer handed over must be demonstrably ingested and correctly pinned — right venue, right date, deduped if related. Those URLs are the implicit test; passing them is the definition of done.

Cut for MVP (stub, don't build): review-queue UI, multi-city, stories cadence, account-discovery loop, ranking beyond a simple score.

Closing the loop

10 Risks, metrics, open questions

Risks

  • IG scraping fragility & ToS — keep it read-only, cached, attributed.
  • Vision hallucination on flyers — mitigated by confidence + evidence + null>guess.
  • Venue mismatch for brand-new / unlisted spots — hold-don't-drop.
  • Dedup threshold tuning — too tight = dupes, too loose = merged distinct events.

Metrics

  • Extraction precision/recall on a hand-labeled set.
  • Dedup false-merge & false-split rate.
  • % events with a confident venue match.
  • Freshness: median lag from post → live on map.
  • “Best”-ranking agreement with a human curator.

Open questions for the founders

  • How much human curation is acceptable vs. fully automated?
  • Is user-submitted content in scope later?
  • Precision vs. recall bias — what's the tolerance for one wrong event on the map?
